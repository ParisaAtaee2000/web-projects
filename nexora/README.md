# NEXORA

فرانت‌اند راست‌چین فروشگاه اشتراک‌های دیجیتال، پیاده‌سازی‌شده با React، TypeScript و Vite. این مخزن شامل رابط مشتری است؛ بک‌اند، پایگاه داده، احراز هویت و پرداخت واقعی در این پروژه پیاده‌سازی نشده‌اند.

## اجرا

```bash
npm install
npm run dev
```

نیازمندی اجرا Node.js نسخهٔ `20.19+` است. نسخه‌های وابستگی‌ها ثابت شده‌اند و `package-lock.json` باید همراه تغییرات نگهداری شود.

برای ساخت خروجی نهایی:

```bash
npm run build
```

## معماری فرانت‌اند

ساختار پروژه بر اساس مسئولیت و قابلیت توسعه تقسیم شده است. هر صفحه و سکشن مستقل است و از کامپوننت‌های مشترک استفاده می‌کند.

- `src/app/`: ترکیب Providerها، مسیریابی و Layout اصلی برنامه
- `src/components/layout/`: هدر، فوتر، منوها، جست‌وجو و بخش‌های فوتر
- `src/components/home/`: سکشن‌های مستقل صفحهٔ اصلی
- `src/components/product/`: کارت محصول و نمایش لوگوی برندها
- `src/components/content/`: لیست مقاله‌ها، ویژگی‌های درباره ما و پرسش‌های متداول
- `src/components/contact/`: اجزای صفحه تماس
- `src/components/ui/`: اجزای عمومی مثل Icon، Breadcrumbs، PageHeading و SectionHeading
- `src/contexts/`: وضعیت مشترک سبد خرید و علاقه‌مندی‌ها
- `src/pages/`: صفحات مستقل فروشگاه، محصول، سبد، سفارش، مجله، راهنما و حساب
- `src/data/catalog/`: داده و مدل محصولات، پلن‌ها و دسته‌بندی‌ها
- `src/data/content/`: داده‌های محتوایی مثل مقالات
- `src/lib/formatters/`: توابع قالب‌بندی و تبدیل نمایش داده
- `src/services/`: لایه درخواست HTTP برای اتصال بعدی به Django REST
- `src/types/` و `src/adapters/`: قراردادهای API و تبدیل داده
- `src/styles/components/`: استایل‌های تفکیک‌شده برای هدر، هیرو، سکشن‌های خانه، کارت محصول، کاتالوگ، جزئیات محصول، سبد، پرداخت، محتوا، تماس، حساب، فوتر، حالت‌های تعاملی و حرکت
- `src/styles.css` و `src/styles.frontend.css`: ورودی و ترتیب بارگذاری استایل‌های کامپوننتی
- `public/assets/`: تصاویر و دارایی‌های سایت

### اصول توسعه

1. هر کامپوننت باید یک مسئولیت روشن داشته باشد.
2. اجزای قابل استفاده در چند صفحه باید در `components/ui` یا پوشه قابلیت مربوطه قرار بگیرند.
3. منطق وضعیت سراسری در Contextها نگهداری شود، نه داخل اجزای نمایشی.
4. دادهٔ محصولات، دسته‌بندی‌ها و مقالات از هم جدا باقی بمانند.
5. نام کلاس‌های CSS و ترتیب سکشن‌ها حفظ شوند؛ refactor معماری به‌تنهایی نباید طراحی را تغییر دهد.

## مسیرهای فعلی

- `/` خانه
- `/shop` فروشگاه و فیلتر دسته‌بندی بر مبنای slug، جست‌وجو و مرتب‌سازی
- `/product/:slug` جزئیات محصول
- `/cart` سبد خرید نمایشی
- `/checkout` فرم اولیهٔ ثبت سفارش
- `/journal` فهرست مقاله‌ها و `/journal/:id` متن مقاله
- `/help`، `/about`، `/contact`، `/account` و `/favorites`

## تحویل به بک‌اند

راهنمای تفصیلی endpointها، نمونه پاسخ محصول و درخواست سفارش در [`docs/backend-handoff.md`](docs/backend-handoff.md) است.

### وضعیت فعلی

- مسیریابی با React Router انجام می‌شود؛ آدرس‌های قبلی حفظ شده‌اند.
- صفحه‌های فروشگاه و جزئیات محصول، در صورت تنظیم `VITE_API_BASE_URL` از endpointهای کاتالوگ داده می‌گیرند و در صورت خطا یا نبود آدرس API به داده‌های نمونه برمی‌گردند.
- فهرست و جزئیات مقاله نیز به endpointهای پیشنهادی مقاله متصل شده‌اند و fallback نمایشی دارند.
- سبد خرید به‌صورت پیش‌فرض در `localStorage` می‌ماند. همگام‌سازی سروری اختیاری است و فقط با `VITE_ENABLE_REMOTE_CART=true` و نشست احراز هویت‌شده فعال می‌شود.
- علاقه‌مندی‌ها فعلاً محلی هستند؛ متدهای API آن‌ها تعریف شده‌اند اما همگام‌سازی حساب‌محور هنوز فعال نشده است.
- Checkout در صورت تنظیم API سفارش را با شناسهٔ idempotency ثبت می‌کند؛ پرداخت خودکار شروع نمی‌شود.
- صفحه حساب، ورود/ثبت‌نام، پروفایل و تاریخچه سفارش را از قرارداد نشست Django می‌خواند. این بخش تا پیاده‌سازی endpointها و توافق CSRF/CORS در حالت غیرفعال می‌ماند.
- فرم تماس و خبرنامه در صورت تنظیم API درخواست می‌فرستند؛ خبرنامه رضایت صریح کاربر را می‌خواهد.
- هیچ بک‌اند، درگاه پرداخت یا دیتابیس واقعی در این مخزن پیاده‌سازی نشده است. داده‌ها و قیمت‌های نمونه برای فروش واقعی معتبر نیستند.

### واکنش‌گرایی

استایل‌ها در فایل‌های component-level زیر `src/styles/components/` تفکیک شده‌اند. بازبینی CSS در breakpointهای دسکتاپ/تبلت (1000px)، موبایل (760px)، موبایل کوچک (430px و 360px) انجام شده و برای کاتالوگ، سبد، جزئیات محصول، مقاله، فرم‌ها، حساب و هدر اصلاحات اختصاصی اعمال شده است. حالت `prefers-reduced-motion` نیز پوشش داده شده است. Build بررسی شده؛ تست بصری روی دستگاه واقعی یا مرورگرهای مختلف هنوز انجام نشده است.

### قرارداد پیشنهادی

مسیرها تا زمان توافق با توسعه‌دهندهٔ بک‌اند قطعی نیستند. پیشنهاد نسخهٔ اول:

| Method | Endpoint | کاربرد |
| --- | --- | --- |
| GET | `/api/v1/categories/` | فهرست دسته‌ها و تعداد محصولات قابل نمایش |
| GET | `/api/v1/products/` | محصولات با `category`, `search`, `ordering` و pagination |
| GET | `/api/v1/products/{slug}/` | جزئیات محصول و پلن‌های اشتراک |
| POST | `/api/v1/auth/register/` | ثبت‌نام؛ روش احراز هویت باید توافق شود |
| POST | `/api/v1/auth/login/` | ورود |
| POST | `/api/v1/auth/logout/` | خروج |
| GET/PUT | `/api/v1/cart/` | دریافت سبد و جایگزینی snapshot کامل اقلام بر اساس `variant_id` |
| GET/POST/DELETE | `/api/v1/favorites/` | فهرست و تغییر علاقه‌مندی‌ها |
| POST | `/api/v1/orders/` | اعتبارسنجی قیمت/موجودی و ایجاد سفارش |
| GET | `/api/v1/orders/` | تاریخچه سفارش کاربر |
| POST | `/api/v1/payments/initialize/` | شروع پرداخت با درگاه مورد توافق |

### شکل داده و پول

- هر محصول `id`, `slug`, `category` و `variants` دارد. هر پلن شناسهٔ مستقل، SKU، مدت، وضعیت موجودی و قیمت دارد.
- قیمت API عدد صحیح با واحد `IRR` است. رابط کاربری آن را برای نمایش به تومان تبدیل می‌کند (۱۰ ریال = ۱ تومان). بک‌اند باید واحد را در تمام پاسخ‌ها صریحاً اعلام کند.
- سبد و سفارش باید بر مبنای `variant_id` و `quantity` باشند؛ slug محصول به‌تنهایی برای خرید پلن کافی نیست.
- بک‌اند منبع نهایی قیمت، تخفیف و موجودی است. قیمت ارسال‌شده از فرانت‌اند قابل اعتماد نیست.
- درخواست ایجاد سفارش باید `idempotency_key` داشته باشد تا ارسال تکراری سفارش نسازد.
- شکل پاسخ خطا، pagination، روش auth، CSRF و CORS باید پیش از اتصال نهایی با تیم بک‌اند هماهنگ شود.

برای تنظیم آدرس API، `.env.example` را به `.env.local` کپی کنید و `VITE_API_BASE_URL` را تنظیم کنید. این متغیر فقط برای اتصال بعدی است و به تنهایی داده‌های نمونه را با API جایگزین نمی‌کند.
